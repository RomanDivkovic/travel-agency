# Architecture

## Scope

Phase 0 creates a modular monolith with a separate React frontend and a single ASP.NET Core API backed by PostgreSQL. Phase 1 builds the public homepage; Phase 2 adds bilingual public information pages, Phase 3 adds a local travel request wizard, and Phase 4 connects it to an independently validated submission API, PostgreSQL and a durable notification outbox. Phase 5 adds Identity-backed administrator authentication and request management. Phase 6 adds versioned quotation approval; Phase 7 adds invoicing and a Development-only simulated payment adapter. Phase 8 adds real-payment-gated manual research and immutable customer proposals. Phase 9 adds evidence-based manual supplier reservation management. There are no microservices, customer accounts, supplier booking execution or live payment-provider integrations.

## Dependency direction

```text
Domain ← Application ← Infrastructure
              ↑              ↑
              └──── Api ─────┘
Tests → Api / Application / Infrastructure
```

Domain references no other project. Application references Domain and defines the database-readiness abstraction. Infrastructure references Application and implements that abstraction with EF/Npgsql. Api is the composition root and references Application and Infrastructure. There are no circular references.

Application and Domain stay free of ASP.NET Core and EF dependencies. Future workflows belong in Application; domain rules belong in Domain; HTTP mapping stays thin. Add validation when concrete request contracts are introduced, rather than installing a validation framework with no current use.

## Frontend

`main.tsx` initializes React, BrowserRouter, self-hosted fonts and global styles. `app/App.tsx` places the localized error boundary inside LanguageProvider, and declares the homepage, five public pages, the travel wizard and confirmation route, a legacy about redirect and the not-found route within the public layout. The Phase 0 `FoundationPage` remains on the development-only `/_dev/health` route with its original health hook and success/failure/pending tests.

`app/config` owns branding and destinations; `content/sv.ts` and `content/en.ts` own typed homepage/shared copy; `content/public.ts` owns bilingual page resources; `content/images.ts` owns responsive media references. `components/ui` provides Button/ButtonLink, Container, Section, Card, and Icon; `components/layout` owns header, brand, mobile disclosure navigation, and footer. `features/home` composes separate section components, keeping the router and page composition small.

Global SCSS is limited to tokens, typography, resets, focus, and reduced-motion rules. SCSS Modules own component layouts and states. Shared SCSS breakpoints provide consistent service grids and navigation. Stateful behavior stays local: header disclosure state and route/anchor focus management. Language is the shared application preference; wizard answers remain local, with draft-storage availability observed externally. There is no state-management or animation framework.

Travel imagery is bundled locally, with responsive WebP and an AVIF hero plus fallback. The hero is prioritized/preloaded; below-the-fold images lazy-load with stable dimensions. Fonts and icons ship their license notices. See [the design system](DESIGN_SYSTEM.md) and [asset provenance](ASSETS.md).

`services/apiClient.ts` centralizes the Axios base URL, timeout, and safe error conversion. `services/health.ts` validates the runtime health payload instead of trusting a TypeScript cast. The hook cancels in-flight work on unmount and handles rejections. SCSS Modules own layout styling; global styles cover typography and basic document defaults.

`VITE_API_BASE_URL` is public configuration embedded at build time. If unset, Axios uses same-origin URLs, suitable for a future reverse proxy. Local development uses the explicit URL in `apps/web/.env`. There is no production API host hardcoded in components.

Swedish is the default language. `localization/LanguageProvider.tsx` initializes from a validated localStorage preference (`travel-agency.language.v1`, only `sv` or `en`), updates the document language and persists explicit choices. Storage errors are caught so switching still works in memory. `useTranslations` and `usePublicCopy` select centralized resources; English shared copy must satisfy the Swedish resource shape. Stable IDs, icon names and image keys are retained across languages. Language switching preserves the route and FAQ disclosure state; prices are not fabricated. No i18n dependency is required for two static languages.

## Travel request wizard (Phase 3)

`features/travel-request/WizardPage.tsx` owns the current step, review-edit mode, validation feedback and draft opt-in. A pure `wizardReducer` owns all form answers; values remain as input strings until payload construction, so empty/in-progress numeric inputs are preserved correctly. `model.ts` defines form data and the separate normalized `TravelRequest` contract. `config.ts` validates service identifiers, derives steps and maps the existing Swedish card IDs to stable service query values. The selected service stays synchronized with the query using replace navigation, so refreshing after a service change cannot reapply an old entry-link selection. Query-only updates retain form state and control focus; start over removes the service query. No new runtime dependency is added.

`steps` separates service selection, trip details, preference fields and personal details. `components/Fields` associates labels and translated errors with controls; `components/Review` renders every relevant answer and an edit action for each section. The existing layout, buttons, route focus and language provider are reused. Copy in `copy.ts` is shape-checked across Swedish/English; language changes keep the current step and answers.

### Dynamic flow and conditional answers

All journeys contain service → destination → dates → travellers → budget → relevant preferences → additional requests → contact → review. Flight and accommodation preferences are separate steps when both apply. Complete planning adds an itinerary/interest step, resulting in 9 steps for either single service, 10 for combined service and 11 for complete planning. Progress is derived from the selected service rather than hardcoded.

- Flights, combined and complete planning require an origin; accommodation alone does not. Flexible destination choice makes a specific destination optional. Only complete planning exposes additional destination stops.
- Fixed-date flight-only requests can be one-way. Accommodation journeys require an end after the start. Flexible mode captures an earliest/latest window and a duration that fits inside it; hidden fixed-date answers are omitted from the payload.
- Children reveal an age entry for each child; reducing the count removes extra ages. Rooms are required only when accommodation is included. Phone is required for phone contact, and any supplied optional phone must still be valid.
- Changing services keeps shared travel/contact answers, resets service-specific preferences, disables one-way mode and resets room count. Irrelevant origin/stops/room/preference fields never enter the final payload. Previous-step navigation keeps current in-memory answers. Review edits revalidate the complete request before returning to review.

### Validation and accessibility

`validation.ts` provides pure field-key/error-code maps for each step plus whole-request validation. It checks trimmed required text and lengths; real calendar dates, local today and a ten-year horizon; ordered date windows; integer duration, counts, ages and rooms; positive bounded budgets with at most two decimals; allowed choice values; email and conditional phone validity. Limits are stated in the UI. Step navigation is blocked on errors, and the payload builder repeats whole-request validation. Phase 4 independently validates untrusted requests server-side; these checks do not establish a server security boundary.

The current step has an accessible heading and aria-current progress. Advancing moves focus to the step heading; errors move focus to a linked summary and use aria-invalid/aria-describedby on fields. Native radio, select, checkbox and fieldset controls support keyboard operation. Start over uses an inline confirmation and restores focus on cancel. The mobile progress view shows the current step, while the full step list remains available on desktop. The confirmation route requires a confirmed receipt; it never invents one.

### Payload boundary

`buildTravelRequest(data, language)` returns `undefined` if any applicable step is invalid. Otherwise it returns an independent normalized `TravelRequest` object: schema version, language, discriminated service/preferences, trimmed destination/origin/optional stops, fixed or flexible dates, numeric adults/child ages/optional rooms, numeric budget/currency/scope, activity assistance, optional special requests and normalized contact details. An omitted return date represents a one-way fixed flight. No request ID, server status, timestamp claiming receipt, quotation or booking is manufactured. Review constructs this object in memory. Explicit send passes it to the API adapter; it is never serialized to browser draft storage.

### Permitted draft persistence

`draft.ts` explicitly projects a safe subset before writing localStorage. Storage is off by default and enabled only by the visitor. Contact details, all free text (including destination/origin/stops) and special requests are excluded even if extra keys are injected into stored JSON. Drafts use version 1 and a seven-day restoration window, reject malformed/oversized records, unknown enums/types, unsupported versions and implausible future timestamps, and reconstruct only known keys. Expiry is enforced on read; abandoned browser storage is not erased by a background service. The next wizard mount removes unusable drafts. Restoration starts at service selection and asks for excluded details again, so incomplete data cannot silently become a valid request.

A small `useSyncExternalStore` subscription observes storage-write availability. Blocked access/quota failures show an honest message while in-memory editing continues. Start over clears in-memory answers, disables opt-in and removes this draft key; if browser storage denies removal, the UI explicitly says it cannot remove the draft and advises clearing site data. Language preference is a separate key and is preserved. Local storage is not encrypted or cross-device storage.

### Phase 4 submission boundary

`services/travelRequests.ts` uses the existing Axios client and validates HTTP 201 and the runtime receipt. `useRequestSubmission` owns pending, validation, uncertain-network, server, rate-limit and conflict states; a synchronous in-flight guard prevents duplicate clicks. Navigation and editing are locked while pending. Server field codes map back to wizard steps. Retry-After controls retry availability; there is no automatic new submission after an error.

`submissionStorage.ts` persists only a UUID and timestamp under `travel-agency.submission-attempt.v1`. It reuses this key after uncertain failures, including remounts. Expired (seven-day), corrupt or unavailable attempt storage blocks sending rather than silently creating a new identity. Start over explicitly warns before discarding an attempt: doing so can create another enquiry if an earlier response was lost. Confirmation clears the matching attempt and permitted draft, with a warning if browser cleanup fails. Receipt-only sessionStorage expires after 24 hours. The success route also accepts the confirmed router receipt when session storage is unavailable. These browser guards are usability controls, not authorization.

## API and persistence

- `/api/health`: liveness without database access; HTTP 200 while the process is responsive.
- `/api/health/ready`: Npgsql connectivity through EF; HTTP 200 or 503. No exception or connection details appear in its JSON response. Connectivity is not proof that future schema migrations are current; migration checks are separate.
- Errors use ASP.NET Core Problem Details. Production responses do not expose stack traces; logs remain server-side. Unknown routes return Problem Details too.
- Development CORS permits configured loopback origins only. Production does not register this policy; a future production origin must be approved and explicitly configured when deployment is implemented.
- The API adds `nosniff`, `DENY` frame protection, and a no-referrer policy. Production uses HTTPS redirection and HSTS. A future reverse proxy must configure trusted forwarded headers and HTTPS correctly.

`TravelAgencyDbContext` maps travel enquiries, hashed idempotency records and notification outbox entries. The original baseline remains intact; the additive `TravelRequestSubmission` migration adds three tables and a reference sequence. Migrations run explicitly through the pinned EF tool; API startup never applies migrations automatically. Design-time tooling reads an environment connection string without inventing fallback credentials.

PostgreSQL Compose configuration is local-only: loopback port binding, persistent named volume, generated local password, and container health check. It is not production infrastructure.

## Verification boundaries

Vitest/Testing Library verify routes, pending/success/failure health states, runtime response validation, and error-boundary recovery. xUnit/WebApplicationFactory verify startup, DI, liveness, readiness success/failure, CORS, safe responses, and headers. The real database test applies the baseline twice against a dedicated test database and checks readiness.

CI uses pinned action commits, dependency lockfiles, isolated PostgreSQL, formatting/linting/type checks, builds, tests, migration checks, and package audits. No production secrets are required.

## Phase 4 persistence and notification architecture

HTTP mapping lives in Api; DTO normalization/validation and orchestration live in Application; the enquiry, contact and travel-plan records live in Domain; EF and transports live in Infrastructure. No additional runtime package was needed.

The accepted schema is version 1 of the existing TypeScript `TravelRequest`: language/service, destination, fixed or flexible dates, travellers, budget, conditional preferences, activity assistance, optional special requests and contact. An optional hidden `website` field must be empty. Unknown JSON members, invalid types and irrelevant service fields are rejected. Dates use the Swedish business calendar; audit timestamps are UTC, rounded to PostgreSQL microseconds. Contact and plan are owned values flattened into the enquiry table; child ages and stops use native arrays, while conditional preferences use JSONB. Status starts as `Submitted`. No customer account is created.

`POST /api/travel-requests` requires a UUID `Idempotency-Key`. Success and identical replays return HTTP 201 with only `referenceNumber`, `status: submitted` and `submittedAt`. The endpoint exposes no request lookup or private database ID. Invalid input returns coded Problem Details (400); a reused key with different normalized content returns 409; oversized input 413; non-JSON 415; throttling 429 with Retry-After; database failure a safe 503. The reader bounds even chunked input at 32 KiB and depth 16. No response includes submitted personal data.

A SHA-256 key hash and canonical typed-payload hash provide replay detection. A PostgreSQL transaction-scoped advisory lock serializes a key, then rechecks it inside the transaction. One commit creates the enquiry, key record and two uniquely constrained notification jobs. An injected failure test proves rollback. References use a configurable uppercase prefix plus UTC year and a global PostgreSQL sequence (`TRV-2026-000001`); gaps are expected and the sequence does not reset annually. A unique index remains authoritative. A reference is not an access credential.

The worker uses `FOR UPDATE SKIP LOCKED` to claim due jobs across workers, holds the row lock through a bounded transport call, then records its outcome. Failures retry exponentially from 30 seconds up to one hour; eight attempts by default, with permanent errors or exhaustion moved to dead-letter state. Saving an enquiry never depends on email availability. HTML output escapes user content and has a plain-text alternative. Customer templates follow the requested Swedish/English language; the agent receives an English operational summary. Notification logs contain IDs and outcomes, not message bodies or contact details.

Development Capture writes one owner-readable JSON file per notification under the API content root `.local-mail`; duplicate IDs reuse the same file. Production rejects Capture. The Resend adapter uses a ten-second HTTP timeout and the stable outbox ID as the provider idempotency key. Delivery is at least once: provider deduplication lasts 24 hours, so a crash after provider acceptance before database acknowledgement can still cause later duplicates. `SentAt` means transport acceptance/capture, not inbox delivery. No external delivery or verified sending domain has been demonstrated locally.

Idempotency records expire after 30 days by default (minimum seven); replay after expiry can become a new request. Hourly worker maintenance removes expired records. Request retention defaults to 365 days, but request deletion is disabled until `Requests__PurgeExpiredRequests=true` is explicitly approved/configured. Enabled deletion cascades notification and key rows. Capture files, backups and provider retention require separate policies. Disabling the worker also disables this maintenance. Production requires explicit retention configuration; legal basis, notices and the approved retention period remain owner decisions.

The fixed-window limiter defaults to ten submissions per IP per minute per API instance. CORS and the honeypot do not replace abuse controls. Deployment must configure trusted proxies, shared edge limits if needed, TLS, private database access and least-privilege credentials. The API never trusts arbitrary forwarded headers. Default logging excludes payloads, email addresses, connection strings and provider response bodies; sensitive-data logging must remain disabled.

Tests cover normalized validation, domain invariants, templates, real PostgreSQL concurrency/replay/rollback, worker retries/dead letters, API failures/rate limiting, frontend submission states and browser-to-database flows. Phase 5 administration and authentication are described below. Quotations, invoices, payments, bookings and deployment remain outside the current phase.

### Personal data and purpose

Enquiries collect name, email, optional phone, preferred contact/language and the requested destinations, travel dates, traveller counts/child ages, budget, preferences and optional free text. These support responding to and preparing the requested travel assistance; they do not create an account or authorize bookings. The UI discourages passport, card and sensitive information. Access is restricted to the backend/database operator and configured email recipients; no public request retrieval exists. Before launch the owner must approve a privacy notice covering controller/contact identity, lawful basis, purposes, processors/transfers, retention, deletion and data-subject rights. Database deletion must be coordinated with backups, capture files and provider copies; the technical defaults alone do not establish GDPR compliance.

## Phase 5 administrator architecture

The existing modular monolith remains in place. Domain centralizes request transitions and holds note/activity records without Identity or EF dependencies. Application defines query/mutation interfaces and DTOs. Infrastructure implements Identity persistence/provisioning, filtered queries and transactional mutations. Api owns cookie/antiforgery composition, centralized role authorization and thin endpoints. The only added package is Identity.EntityFrameworkCore 10.0.14, matching the established framework patch; no frontend dependency was added.

### Authentication and authorization

ASP.NET Core Identity stores salted framework password hashes, role membership, lockout state and security stamps in the existing PostgreSQL database. Only the `Administrator` role satisfies the shared policy. Login is generic for unknown users, wrong passwords, lockouts and unsupported second-factor accounts. Passwords require 12 characters with uppercase/lowercase/digit/symbol. Five failures lock an account for 15 minutes; the endpoint additionally permits ten attempts per IP per minute per process. No registration or password-reset endpoint is exposed.

The application cookie is HttpOnly, SameSite Strict, path `/`, without a broad domain. Production uses a `__Host-` name and Secure Always; local HTTP development uses a separate cookie name and SameAsRequest. Sessions expire absolutely after 30 minutes by default (configurable 1–120), do not slide and are browser-session cookies rather than remember-me cookies. Identity validates security stamps on every authenticated request. Logout rotates the stamp and signs out, invalidating every session for that administrator on its next request. No cookie value, password or bearer token is stored through frontend JavaScript.

`GET /api/admin/auth/csrf` issues the framework antiforgery cookie and request token. Every admin POST/PATCH, including login/logout, validates the request token from `X-CSRF-TOKEN`. The frontend fetches a fresh token before each mutation, including after an authentication identity change. Tokens live only in memory. Anonymous data access returns 401; an authenticated principal without the role returns 403. Both are distinct from 400 antiforgery/input errors. All admin responses carry no-store, and API CSP denies rendering/scripts/framing. Public submission stays anonymous and does not use administrator cookies for authorization.

Development CORS allows credentials only for explicit configured loopback origins. Vite 5173 and API 5080 are different origins but the same localhost site, so Strict cookies work with Axios `withCredentials`. A different hostname (including 127.0.0.1) is not interchangeable. Production currently has no cross-origin CORS policy; deploy behind an approved same-origin HTTPS reverse proxy or separately review an exact credentialed origin policy. Do not loosen to wildcard origins or SameSite None as a shortcut.

### Administrative API

| Endpoint | Behavior |
| --- | --- |
| GET `/api/admin/auth/csrf` | Anonymous-safe antiforgery bootstrap |
| POST `/api/admin/auth/login` | Email/password; antiforgery + IP limit; safe administrator DTO |
| POST `/api/admin/auth/logout` | Authorized, antiforgery-protected, revoke sessions; 204 |
| GET `/api/admin/auth/me` | Authorized ID, display name, email and Administrator role only |
| GET `/api/admin/dashboard/summary` | Database status counts and five latest updated requests |
| GET `/api/admin/travel-requests` | Validated server-side search, filters, deterministic sorting/pagination |
| GET `/api/admin/travel-requests/{uuid}` | Complete enquiry DTO, concurrency version and allowed next statuses |
| PATCH `/api/admin/travel-requests/{uuid}/status` | `{status, version}`; transition + optimistic concurrency; 204 or 409 |
| GET/POST `/api/admin/travel-requests/{uuid}/notes` | Paged chronological notes / `{content}`; authenticated author; 204 on creation |
| GET `/api/admin/travel-requests/{uuid}/activity` | Paged chronological immutable history |

All data/mutation endpoints require the administrator policy independently of frontend routing. Missing UUID records return 404, invalid inputs/filters 400, stale versions/concurrent writes 409. Framework Problem Details handles unexpected errors without exposing entities, hashes or exception details.

List parameters are `page` (1–100000), `pageSize` (1–100, default 20), `status` (case-sensitive enum name), `serviceType` (existing four service strings), `search` (up to 150 characters), `sort` (`createdAt_desc`, `createdAt_asc`, `updatedAt_desc`), `from`, and `to` (ISO dates, inclusive UTC submission dates). Search uses escaped, parameterized PostgreSQL ILIKE over reference/name/email. Literal percent/underscore characters are escaped. Pagination uses Count plus ordered Skip/Take in SQL, with UUID tie-breaking. Responses include items, page/pageSize, totalCount/totalPages and exclude notes/contact email from list cards. Small-scale substring search is acceptable initially; production volume may justify reviewed trigram indexes and keyset pagination.

### Workflow and persistence

`Submitted → UnderReview` or `Closed`; `UnderReview → AwaitingCustomer` or `Closed`; `AwaitingCustomer → UnderReview` or `Closed`. Closed is terminal in Phase 5 and does not mean booked. Quotation/payment/booking state remains separate and unimplemented. The domain supplies permitted transitions; APIs validate them again and the frontend displays only allowed values.

The additive `AdminDashboard` migration adds standard Identity tables, a GUID concurrency token and status constraint update, request service/updated indexes, notes and activity tables. Existing Phase 4 enquiries receive generated versions and a submitted event at their original creation timestamp. No enquiry data is deleted. Notes reference the enquiry and authenticated author, limit plain text to 4000 characters and use UTC timestamps. Activity records retain only event type, actor, previous/new status and UTC time, never the note body. Request deletion cascades notes/history; author deletion is restricted to preserve provenance. Existing retention maintenance therefore covers request-linked admin data too. Administrator-account retention requires separate operational review.

A status change updates the domain version/timestamp and adds activity in one SaveChanges transaction. Notes also touch the enquiry and record their activity atomically. EF compares the original version in UPDATE; concurrent changes roll back the entire write and return 409. No status-change emails are sent. New public submissions create their submitted activity in the existing request/outbox transaction. Public receipts and customer emails do not expose notes, admin activity or internal IDs.

### Frontend and session state

`features/admin` separates authentication context, API adapter, cancellable query hook, login/layout, dashboard/list/detail pages, fields/actions/timeline, copy and SCSS. Protected routes gate rendering after `/me`; safe return paths are restricted to known admin route shapes. Expired 401 responses clear the auth context and unmount protected data. A generation guard prevents older session checks restoring authentication after logout/invalidation. Initial page load, window focus and a 60-second check refresh the session. In-flight reads are aborted on key/route changes; stale responses cannot replace a newer query. Mutations reload detail/version and timelines; list/dashboard are freshly loaded when visited. There is no persistent private-data cache and no Redux/query dependency.

Search/filter state stays in memory (not URL, localStorage or analytics). Names, contact, notes and activity are escaped React text; there is no trusted HTML or rich-text editor. Preference labels reuse the wizard localization resources, while admin strings use the existing Swedish-default language provider. Request cards reflow instead of imposing a wide table on phones; sidebar navigation wraps into a compact navigation block on smaller screens. Admin metadata stays noindex and omits canonicals and customer names.

### Production security boundary

This phase does not claim production readiness. Implement/review standard TOTP MFA enrollment, verification, recovery codes and recovery procedures before exposing customer information. Identity token-provider/storage capabilities are retained, and a two-factor-enabled account cannot bypass its second factor through this password-only endpoint. Password recovery/rotation is a controlled operator task until a reviewed workflow exists. Do not disable MFA to work around missing UI.

Provision data-protection keys on persistent restricted storage, with encryption at rest and sharing only across intended API instances; default local key handling is insufficient for a deployment guarantee. Review HTTPS/proxy trust, secure hosts/origins, frontend admin no-store/CSP headers, session policy, centralized throttling for multiple instances, least-privilege database access, backups and account recovery. No customer analytics are introduced. Operator access is limited to authenticated administrators and database/backup operators; privacy notices/retention and legal policies still require owner approval. These technical controls alone do not establish GDPR compliance.

## Phase 6 quotations and customer approval

Phase 6 extends the same modular monolith and existing admin/outbox infrastructure. Domain owns quotation transitions, revision rules and monetary calculations; Application defines dedicated draft, issuance, customer, query and expiry boundaries. Focused Infrastructure implementations use EF transactions and token protection. Api provides thin policy/antiforgery-protected admin endpoints and a narrow bearer-token customer API. Infrastructure explicitly references the existing ASP.NET shared framework for Data Protection; no new NuGet or frontend package is installed. Existing authentication and public enquiry contracts remain operational.

### Model and lifecycle

Each non-Closed request can have one numbered `QuotationSeries`. Its database sequence-generated number is unique (configurable `QUO` prefix, UTC year, globally increasing suffix; gaps are normal and numbering does not reset annually). A series contains distinct version records, each with its own UUID, integer version, optimistic version token, immutable issued scope/price/terms, customer name/email/language snapshots, creator, UTC audit/deadline/response timestamps and calculated line items. A unique `(SeriesId, Version)` index and partial unique active-version index covering Draft/Sent/Accepted prevent conflicting offers. Number uniqueness belongs to the series, not each historical version.

Drafts can be edited or cancelled. Sent versions can be accepted, declined, expired, superseded or cancelled. Accepted versions are terminal and cannot be revised or edited. Only the current Sent, Declined, Expired or Cancelled version can produce a new draft revision; Draft is edited in place. Revising Sent immediately marks it Superseded and revokes its link, even before the new draft is sent. A genuinely expired version retains Expired when revised. Historical prices and terms are never overwritten. A cancelled replacement does not reactivate an older offer. One series per enquiry avoids duplicate concurrent initial offers; revisions reuse its number with incrementing versions.

All mutations and customer decisions acquire the same PostgreSQL series row lock. Initial creation uses a namespaced transaction advisory lock plus the unique request association. Admin operations additionally require the displayed GUID `versionToken`; stale writes conflict. Revision releases the old active-version slot with an intermediate SaveChanges inside the same transaction, then inserts the replacement and commits both atomically. Version content, activity, token and notification intent remain transactional. No generic status update endpoint can bypass domain rules. Request status stays separate: quotation acceptance never implies payment, completed research or a booking.

### Monetary integrity and approval gates

Only SEK, EUR and USD (two fractional digits) are currently supported. Amounts are integer minor units (`bigint`), never binary floating point. Each quotation supports 1–20 lines, integer quantities 1–100 and bounded nonnegative unit prices. The total is bounded at 10,000,000,000 minor units; issuing requires a positive total. Zero-priced drafts are placeholders, not free issued offers.

Tax treatment is explicit: Unconfirmed (draft only), VatExclusive (add tax), VatIncluded (extract tax), or NoVat (no tax charged). No treatment or rate is inferred from the business's Swedish location. Rates use integer basis points (0–10000); Unconfirmed/NoVat lines require zero. Exclusive line tax is rounded from `quantity × unitMinor × rate / 10000`; inclusive tax from `grossMinor × rate / (10000 + rate)`. Rounding is to integer minor units, midpoint away from zero, separately per line; quotation totals sum the rounded lines. The browser previews the same positive-integer arithmetic, but sends no totals. The backend always recalculates authoritative amounts and validates currency, quantity/rate/text/deadline limits.

Issuance requires an explicit enabled setting, approved treatment/rate allowlists, configured bilingual terms and acceptance text, terms version and approved public origin. The draft terms must match the configured approved text for the customer's language; service-specific included/excluded scope remains editable. Issue freezes terms/version and the acceptance wording in that version. Configuration changes affect future issuance, not previously issued contracts. No legal template or tax exemption/rate is invented. Exact consumer acknowledgements, cancellation/withdrawal rights, VAT and service-performance terms require owner/adviser review before commercial use.

### Limited customer credentials

The server creates 32 cryptographically random bytes encoded as a 43-character base64url credential. Only SHA-256 is stored in `QuotationTokens`, with an exact quotation-version association, access expiry and revocation timestamp. The emailed link uses `/quote#credential`: fragments are not sent in HTTP requests, so access/proxy URL logs never receive it. The SPA sends the credential only through `X-Quotation-Token` to fixed `/api/public/quotations` routes. It never enters query strings, metadata, analytics, localStorage or sessionStorage. Browser history and the email still contain the private link by design; the UI warns against sharing it or using shared devices. Numbers and UUIDs grant no customer access.

The issued-email outbox must recover the link for durable delivery, so that envelope is encrypted using the existing ASP.NET Data Protection key ring with the isolated `TravelAgency.Quotations.DeliveryLink.v1` purpose. This recoverable delivery envelope is separate from the hashed authorization lookup; no plaintext token is stored in the database. The envelope is cleared after transport acceptance or suppression, and hourly maintenance clears envelopes whose access token expired. Failed deliveries retain encrypted envelopes for bounded retries. Production requires persistent restricted/encrypted keys, including across intended instances/restarts; losing them prevents pending-link delivery. This is an operational prerequisite, not a guarantee from local defaults.

Tokens expire after the quotation deadline plus a configurable 30-day read window (range 1–90). ### Decisions, expiry and history

GET only reviews. Explicit JSON POST plus the bearer header records an accept/decline; a link scanner or cookie alone cannot decide. The acceptance checkbox starts unchecked and displays the frozen, configured acknowledgement. Accept records its exact quotation version, UTC timestamp and accepted terms version, with the immutable terms snapshot retained. Same-decision retries return the original state without changing timestamps or generating new jobs; opposite decisions and invalid states conflict. This is technical acceptance evidence, not a claim of verified legal identity or a qualified electronic signature. No customer account is created.

Validity is a UTC instant (future, at most 366 days when saving); editors label their browser time zone, and views display localized instants. Quotation emails explicitly display Europe/Stockholm and its actual offset. Every customer read/decision checks the current state/deadline inside the series lock. Acceptance cannot race a revision, cancellation or expiry into conflicting results. The existing worker also expires up to twenty due Sent records per polling cycle and records each transition once. Synchronous enforcement remains authoritative if the worker is unavailable.

Existing request activity is extended with an optional quotation foreign key and projected version. Events cover creation/editing/issuance/revision/supersession/cancellation/acceptance/decline/expiry; only structured states and actor/time are stored, not note bodies or tokens. Admin quotation history is paginated across all versions; expiry is attributed to System, decisions to Customer, and admin actions to the authenticated actor. ## Phase 7 invoices and service payments

### Invoice snapshots and lifecycle

Phase 7 now consumes the Phase 6 accepted-version boundary described above. `Invoice.Create` requires an accepted, positively priced quotation, copies the exact integer-minor-unit totals and ordered line/tax snapshots into immutable JSON, and retains the quotation UUID/version/number, customer name/email/language and request association. Issuance freezes approved seller identity/address/registration/tax information, language-specific invoice terms/version, issuance timestamp and final number. Future configuration changes do not change issued invoices.

Lifecycle: Draft → Issued → PaymentPending/Paid/Overdue; Overdue → Paid. Draft alone can be cancelled. Issued cancellation, financial corrections, credit notes and refunds are unavailable until an approved accounting workflow exists. No administrative “mark paid” endpoint exists. Payment failure/cancellation belongs to payment attempts and leaves the invoice unpaid/payable. The worker detects overdue invoices without late fees, debt collection or reminders; verified late payments can settle them.

One primary invoice per accepted quotation is database-enforced, including cancelled drafts; replacements require a future approved correction workflow. Issuance locks a single persisted invoice-number counter inside the transaction, producing `INV-yyyy-000001` (or explicit `TEST-INV` for simulation). Rollback does not consume an invoice number, numbers are not reused and the monotonic counter does not reset at year boundaries. This design must be approved by the owner's accountant before commercial use.

### Provider boundary and evidence

`IPaymentProvider` separates session creation, webhook verification and provider reconciliation from application rules. No provider approval, account, merchant-of-record arrangement or credentials were supplied. The default adapter is Disabled. The only implemented adapter is **Sandbox**, an in-app Development-only simulator that cannot start in Production. It is not Stripe, an official provider sandbox or real money movement. It persists separate provider evidence in `SandboxPayments`, supports explicit simulated Pending/Succeeded/Failed/Cancelled outcomes and uses HMAC-SHA256 over `timestamp.rawBody`, fixed-time signature comparison and a five-minute timestamp tolerance. Its merchant context is fixed to `development-simulator`. This protocol must never be reused as a substitute for a future live provider's official SDK/verification requirements.

The browser sends no amount/currency to session creation. Invoice locks serialize creation; the attempt UUID is the adapter idempotency key. A still-valid pending attempt reuses its session. Failed/cancelled/expired sessions allow a new attempt; delayed success is still processed. Sandbox checkout is a clearly labelled same-origin `/payment/sandbox#credential`, with no card form. Returning to `/payment/result#invoiceCredential` does not settle anything; backend state drives results and bounded polling. Live hosted checkout and real reconciliation remain blocked pending provider approval/integration.

Verified events must match the stored invoice, provider session, amount, currency and adapter mode. A durable unique `(Provider, EventId)` record, event advisory lock and invoice row lock serialize replay/concurrency. Provider session/payment identifiers also have unique constraints. Payment, paid timestamp, activity, eligibility and unique outbox intent commit in the same transaction. Success is monotonic against delayed failure/cancellation. A second successful attempt is retained with an `additional-payment-review` discrepancy; it cannot duplicate activation or confirmations. Mismatched amount/currency records a discrepancy without settling. No raw webhook bodies or payment credentials are retained/logged.

The existing background worker runs bounded reconciliation (10 due pending attempts/poll, eight claims/attempt with exponential delays capped at six hours) and overdue detection (20 invoices/poll). A claim is locked and committed before querying evidence, so multiple workers cannot continuously reclaim the same payment. Provider failure leaves state unpaid and records a safe discrepancy code. Exhausted attempts remain visible for operator review; no automatic manual-payment override is provided. Reconciliation calls the same event/state processing as webhooks.

## Phase 8 travel research and proposals

### Eligibility and workspace

### Manual supplier records

### Proposal model and pricing

Source notes/version metadata never appear publicly. Removing referenced research options is blocked; deleting old draft associations occurs transactionally before replacement order slots are saved.

Draft saving refreshes selected snapshots from this request's current research items, rejects foreign-request IDs and checks per-currency limits. Sending rejects source-version changes since the last saved draft, requiring the agent to save/review again. Editing research after sending does not change the issued proposal. Supplier estimates group by currency and separately show flight/accommodation/extra subtotals; no mixed-currency grand total exists. The paid service fee has its own already-paid section and is never added again to supplier amounts due. Optional extras included in an alternative contribute to that alternative's estimates; the customer approves one complete primary alternative, not an ambiguous partial bundle.

### Lifecycle, immutable versions and decisions

Draft → Sent/Cancelled; Sent → Approved/Rejected/Expired/Superseded/Cancelled. Sent contents are immutable. Alternative/item snapshots expose read-only domain properties and collections. Revision is available for Sent/Rejected/Expired/Cancelled current versions; it clones snapshots into a new Draft with new alternative IDs and deadline, preserves old versions and immediately revokes the previous link. Approved is terminal in Phase 8. One active Draft/Sent/Approved slot per series is database-enforced. Cancelling a current eligible draft/sent version revokes its access, but expiry wins at the deadline. No supplier booking or service-fee refund is caused by decisions.

Request row `FOR NO KEY UPDATE` locks serialize workspace/options/proposal mutations and customer decisions while remaining compatible with foreign-key key-share locks in the payment/outbox workflows. Optimistic version tokens prevent stale browser edits. Proposal/version uniqueness, foreign keys, selected-alternative/decision records and transaction boundaries protect history. Creation uses a PostgreSQL sequence (gaps permitted; this is not invoice numbering). Sending freezes reviewed terms/version/acknowledgement and queues encrypted-link outbox intent atomically.

Customers choose an alternative explicitly; no radio or approval checkbox is preselected. They review that alternative's estimated currency-separated costs, acknowledge frozen terms and confirm a second explicit approval step. The backend checks scoped token/current version/deadline, exact terms version, real eligibility and membership of the selected alternative. Same decision/selection replay is idempotent; opposite decisions or a different approved alternative conflict. The immutable decision stores alternative, timestamp, terms/acknowledgement and optional rejection feedback; it does not record unnecessary IP/device data. Background expiry (20 due versions/poll) and synchronous response enforcement share the existing worker and are idempotent.

## Phase 9 — Booking management architecture

`Domain/Bookings` centralizes booking status calculation, customer authority/evidence validation, supplier reservation transitions, price/term review and cancellation rules. `Application/Bookings` owns DTOs. Existing request activity links booking summaries without exposing detailed evidence publicly. Notes remain private. Booking mutations lock the parent request followed by the aggregate row, verify a client version token and persist state/history/outbox atomically. The unique booking/request/proposal/reference constraints and restrictive FKs preserve financial/proposal history. Migration `20261102155928_BookingManagement` adds tables and nullable activity/outbox columns; older migrations remain unchanged.

Full-trip email is an explicit idempotent queue operation per booking revision, allowed only when all reservations are genuinely Confirmed. The existing outbox retains a customer-safe immutable confirmation snapshot; worker delivery locks the booking row and discards full-confirmation jobs whose aggregate revision/status changed. Writers never lock outbox rows, avoiding inverse lock ordering. Retry/backoff, capture/provider sender, delivery status and HTML escaping reuse existing infrastructure. Failure notifications go only to the agent and preserve other confirmations. No partial trip is represented by the full-confirmation template. The at-least-once email limitation still applies.

Pages reuse cancellable resource hooks, API client/auth, UTC/zoned travel fields, money formatter and saved proposal preview. SCSS Modules provide responsive cards/forms. Explicit saves/actions report success only after server acknowledgement; no autosave or supplier execution is implied. Swedish/English resources preserve Swedish default and customer-preference email language. All estimates/current costs remain grouped by original currency and separate from the paid service fee.

Phase 10 may read immutable approved proposal and actual confirmed reservation facts for later portal work. Document upload/generation, itinerary management, customer accounts/messaging, automatic supplier operations/refunds and supplier payment collection remain deferred.

Public account routes are `/register`, `/login`, `/forgot-password`, `/resend-verification`, `/verify-email`, `/reset-password` and `/confirm-request`. Protected routes are `/account`, `/account/requests`, `/account/quotations`, `/account/invoices`, `/account/proposals`, `/account/bookings`, their `/:id` detail routes, `/account/profile` and `/account/security`. Private routes are noindex and omit public canonical metadata. Server lists are paginated (20 rows), scoped, filtered and sorted before materialization. Dashboard data is bounded; journey derivation is batched.

Customer APIs live under `/api/customer`: `/auth/{register,login,logout,me,csrf,verify-email,resend-verification,forgot-password,reset-password,change-password}`, `/profile` (GET/PATCH), `/profile/language` (PATCH), `/requests/{claim,confirm-claim}`, `/dashboard`, `/activity`, and paginated `/travel-requests`, `/quotations`, `/invoices`, `/proposals`, `/bookings`. Detail GETs use GUID IDs; quotations accept/decline, proposals approve/reject, invoices payment-session/document reuse existing rules. Cookie mutations require antiforgery. Account/auth routes are rate limited; all customer responses are no-store and no-referrer. Supplier URLs are never fetched automatically.

Phase 11 boundary: no new document storage/download system, itinerary generator, messaging, supplier automation or additional supplier payment collection. The invoice download is the already-existing HTML invoice document. Profile email changes are deferred pending a separate dual-verification design. Session security exposes the current absolute expiry and global revocation, not an invented list of device sessions.

The persisted browser test harness lives in the test project and `apps/web/e2e`; it is opt-in, guarded by `_e2e_tests` naming and has no production seed route. It launches separate API/production-preview servers, uses the existing local mail-capture adapter, and disposes its synthetic records. The current verification evidence and production limits are recorded in `docs/DEVELOPMENT.md`.

## Phase 11 — private documents and versioned itineraries

`Domain/Documents` centralizes publication and local-time rules; typed application contracts separate administrative and customer projections. Focused infrastructure services implement document operations/storage/scan, itinerary generation/operations/PDF, publication mail and bounded maintenance. Thin endpoint groups reuse the existing administrator/customer authorization policies, CSRF, request/booking lock order, no-store headers, activity and outbox. React's lazy `travel-documents` feature reuses auth, API/resource hooks, localization and SCSS Modules; shared timelines and safe file actions serve both audiences.

### Document storage and lifecycle

`TravelDocuments` identifies a booking and optional same-booking reservation, category, current version and published version. `DocumentVersions` stores customer-visible metadata, MIME/size, uploader, scan state and lifecycle per immutable file. Draft metadata can change, but replacements create a new file/version. Only the clean current draft can publish; reservation-specific publication additionally requires a confirmed reservation. A new draft does not replace the previous customer publication. Publishing archives the previous version. Archive/delete remove customer access immediately; file deletion is durable background work.

`DocumentBlobs` is an internal cleanup ledger with random 256-bit keys, never returned to clients. A committed one-hour lease precedes storage writes, making interrupted uploads/transaction rollbacks collectible. Attaching the version clears the lease transactionally. Booking deletion sets the ledger booking association to null while document metadata cascades, allowing orphan-file collection. Maintenance retains draft/archived versions for configurable periods, marks due files deleted, clears filenames/descriptions after physical deletion, and retries failures with bounded backoff. Database/file deletion cannot erase external backups; production retention procedures must cover backups and keys separately.

`ITravelDocumentStorage` separates private binary operations. Development's `LocalEncrypted` adapter stores Data Protection-encrypted bytes outside the repository/public tree, restricts directory/file modes, validates random keys, rejects direct symlinks and writes atomically. Production defaults to `Disabled` and rejects this development adapter. Key persistence and a reviewed production storage implementation are prerequisites to commercial use.

Uploads use bounded multipart parsing/copying (default 10 MiB), normalized basename filenames and matching allowlisted MIME/extension/signatures. Signature checks are an initial format gate, not complete PDF/image parsing. The server never fetches supplier URLs. A real ClamAV `INSTREAM` adapter accepts only a complete explicit clean result; errors, timeout or incomplete results remain quarantined, and detections are rejected. Neither state permits preview/download/publication. Scanner TCP is restricted to loopback. HTML/SVG/executables, passports and identity documents are not supported. Customers cannot list unpublished/history versions or unrelated bookings. Downloads recheck ownership/publication under booking locks, return attachments with no-store headers and never disclose storage paths. Client previews use revoked object URLs, escaped text and an opaque-origin sandboxed PDF iframe; download remains available if a browser's PDF viewer cannot run in that sandbox.

### Itinerary snapshots and time

`ItinerarySeries` is unique per booking with current/published version pointers and an optimistic token. `ItineraryVersions` holds title, customer description, booking revision, typed trip and entry JSONB snapshots, actor and lifecycle timestamps. Entry snapshots remain inside each version rather than duplicating mutable rows across versions. Generated entries preserve internal reservation/arrangement/source keys; public DTOs expose only customer-safe fields. Version pairs, FKs, concurrency tokens and booking/request locks protect consistency.

Generation uses confirmed current supplier reservations only: each flight leg has separate departure/arrival entries, accommodation has date-only check-in/out, and extras retain recorded dates without inventing meeting times. Generated source keys deduplicate refreshes; custom entries survive regeneration and cannot carry supplier authority. Timed custom entries require IANA timezone and a valid local time; DST gaps are rejected and ambiguous times require an explicit matching UTC offset. Supplier-local date/time controls grouping and ordering, including overnight/multi-leg journeys. Unknown times remain explicitly unspecified. Generated travel date bounds derive from the confirmed entries.

Drafts can be edited and regenerated. Publication requires a confirmed entry and matching booking revision. Published content is frozen; revision copies it into a new private draft. The previous publication remains customer-visible until the new version supersedes it. Booking changes surface a warning without silently rewriting history. Custom information is explicitly distinguished from supplier-confirmed arrangements. PDFs are generated from the same safe snapshot using MIT-licensed PDFsharp/MigraDoc 6.2.4 and bundled SIL Open Font License Noto Sans. They include branding, booking/version, dates/travelers, source-local times/offsets, references, generation timestamp and pagination; administrator drafts are labelled.

### Routes, contracts, migration and notifications

Admin pages: `/admin/bookings/:id/documents` and `/admin/bookings/:id/itinerary`; customer pages use `/account/bookings/:id/documents` and `/account/bookings/:id/itinerary`. Booking detail pages link to both. API groups live at `/api/admin/bookings/{bookingId}` and `/api/customer/bookings/{bookingId}`.

Admin document operations: GET/POST `documents`; POST `documents/{id}/replace` (multipart `file`, JSON `metadata`, replacement `versionToken`); PATCH `documents/{id}`; POST `documents/{id}/{publish,archive,delete,scan}`; GET `documents/{id}/download?version=N`. Metadata includes name, description, type, optional reservationId and mandatory `noIdentityDocuments: true`; changes require the optimistic token and version. Libraries use server-side pagination, 20 document series/page. Customer endpoints are GET `documents` and GET `documents/{id}/download`, restricted to the current clean published version.

Admin itinerary operations: GET/POST/PATCH `itinerary`, POST `itinerary/{generate,publish,revise,archive}`, GET `itinerary/pdf?version=N&language=sv|en`. Save accepts title, description and custom entries only; generated supplier fields cannot be supplied by that contract. Customer endpoints are GET `itinerary` and `itinerary/pdf?language=sv|en`; the default PDF language is the customer's preferred language. Customer projections omit optimistic tokens, storage keys, internal notes, source keys and arrangement versions.

Migration `20261105161812_TravelDocumentsItineraries` adds five tables with indexes/FKs/version uniqueness, and expands outbox kind length to accommodate per-version notification IDs. Existing request/financial/account data is retained. Publications atomically queue localized portal-link notifications; no sensitive file attachments or public storage links are emailed. The worker suppresses archived/superseded notifications and reuses existing retries/capture/delivery semantics. Publication, access and changes reuse booking/customer activity infrastructure. File maintenance runs within the existing worker with isolated failures. Phase 12 remains outside this implementation.
