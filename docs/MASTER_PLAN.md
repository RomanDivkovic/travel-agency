PART 1 — BUSINESS CONCEPT

1. Business Vision

Create a modern, trustworthy, personalized travel agency where customers receive professional help finding, planning, and booking their trips.

The business will initially be operated by an experienced travel agent who offers her services independently during her available time.

The goal is to help customers save time, reduce the stress of organizing travel, and find suitable travel arrangements based on their budget and preferences.

Unlike traditional travel booking websites, customers will not need to search through hundreds of options themselves.

Instead, they explain their requirements, and a real travel agent handles the process.

Core Value Proposition

“Tell us where you want to go. We’ll help you find, plan, and book the right trip.”

The business should emphasize:

* Personal service.
* Professional travel industry experience.
* Budget-conscious travel recommendations.
* Convenience.
* Transparent pricing.
* Individual attention.
* Reliable communication.
* A simple booking process.

The business should not promise the cheapest available prices.

Instead, it should promise to research suitable options and help customers make informed travel decisions.

6. Customer Payment Model

The platform must distinguish between:

Service fees: Payment for the travel agent’s professional work.

Travel costs: Payments for flights, hotels, and other travel arrangements.

The initial operational model should be:

1. Customer submits a request for free.
2. Agent reviews the request.
3. Agent prepares a service quotation.
4. Customer accepts the quotation.
5. Customer pays the agreed service fee.
6. Agent begins researching suitable travel options.
7. Agent presents travel recommendations.
8. Customer approves the selected arrangements.
9. Travel costs are paid through the legally approved payment arrangement.
10. Agent completes the bookings.
11. Customer receives confirmation documents.

No paid research or booking work should begin before the agreed service fee has been received.

However, the system must allow the owner to configure different legally compliant payment workflows in the future.

The business must define how travel costs are collected, how supplier payments are made, and who is contractually responsible for each booking before launch.

The business will operate in Sweden.

Before accepting commercial bookings, investigate and establish:

* Appropriate business registration.
* Tax and VAT treatment.
* Accounting and invoicing procedures.
* Consumer protection obligations.
* Package travel legislation.
* Travel guarantee requirements.
* Liability and insurance.
* Supplier booking permissions and agreements.
* Cancellation and refund policies.
* GDPR compliance.
* Customer data retention policies.
* Required customer information before booking.

Relevant Swedish authorities include Kammarkollegiet, Konsumentverket, and Skatteverket.

The platform must support compliance but must not assume the business already meets these requirements.

Commercial launch is blocked until the owner has confirmed the applicable legal and operational requirements.

15. Development Standards

The project must remain maintainable throughout development.

Requirements:

* Use TypeScript strict mode.
* Separate business logic from UI components.
* Keep files focused.
* Avoid oversized components and services.
* Extract reusable functionality.
* Use shared custom React hooks where appropriate.
* Separate API contracts and validation.
* Use consistent naming conventions.
* Include meaningful error handling.
* Add tests for critical business rules.
* Maintain clean database migrations.
* Use accessible UI components.
* Do not hardcode business prices.
* Do not hardcode sensitive credentials.
* Do not simulate successful payments or bookings in production.

Avoid monolithic files.

If a file grows excessively large, refactor it during the same phase.

Files approaching 2,000 lines must be treated as an architectural problem, not an acceptable default.

Prefer much smaller, cohesive modules.

PART 8 — INSTRUCTIONS TO THE AI CODING AGENT

CRITICAL: READ BEFORE IMPLEMENTATION

This document is the complete project vision and development roadmap.

It is NOT an instruction to implement the entire application immediately.

You must follow the phased development process.

Rule 1 — Understand the Master Plan

Read the entire document before making architectural decisions.

Understand the business model, customer journey, and long-term requirements.

Design the foundation so future phases can be implemented without unnecessary rewrites.

Do not implement future-phase features prematurely.

Rule 2 — Implement One Phase at a Time

You will receive a separate implementation prompt for each phase.

Only implement the explicitly assigned phase.

Do not begin another phase without authorization.

Rule 3 — Inspect the Repository

Before every phase:

1. Inspect the current Git status.
2. Identify the active branch.
3. Preserve existing work.
4. Review the current architecture.
5. Identify functionality already implemented.
6. Avoid duplicating existing features.

For phases after the first, when previous work has been merged and the working tree is clean:

1. Checkout the main branch.
2. Pull the latest changes.
3. Delete the previous local phase branch if it is safely merged.
4. Create a new branch for the assigned phase.

Never discard uncommitted work.

Never delete unmerged branches.

Rule 4 — Maintainability

Every phase must:

* Follow clean architecture principles appropriate to the project.
* Avoid oversized files.
* Keep UI components focused.
* Extract shared hooks and utilities.
* Keep styling separate where appropriate.
* Maintain clear boundaries between frontend and backend.
* Include appropriate tests.
* Preserve existing functionality.

Refactor excessive complexity within the current phase.

Do not postpone necessary maintainability work indefinitely.

Rule 5 — Scope Control

Do not introduce unrelated functionality.

Do not build features from future phases unless they are essential prerequisites for the current phase.

If a future dependency is required, implement the smallest appropriate abstraction.

Avoid unnecessary dependencies and architectural complexity.

Rule 6 — Testing

Every phase must include appropriate verification.

Run relevant:

* Builds.
* Lint checks.
* Type checks.
* Unit tests.
* Integration tests where appropriate.

Fix failures introduced by the phase.

Do not claim checks passed unless they were actually executed.

Rule 7 — Documentation

At the end of each phase, provide:

1. Summary of implemented functionality.
2. Important architectural decisions.
3. Files added or modified.
4. Tests executed and results.
5. Known limitations.
6. Remaining work.
7. Confirmation that the phase is ready for review.

Rule 8 — Git Workflow

Use descriptive phase branches.

Examples:

phase-0-project-foundation

phase-1-homepage-design

phase-2-public-pages

Do not automatically merge into main unless explicitly instructed.

Prepare changes for review.

Rule 9 — Definition of Done

A phase is complete only when:

* Assigned requirements are implemented.
* Existing functionality remains operational.
* Relevant tests pass.
* Code follows maintainability standards.
* Documentation is updated.
* No known critical bugs remain.
* Changes are ready for review.

Rule 10 — Wait for the Next Phase

After completing a phase, stop.

Do not automatically start the next phase.

Wait until the user provides the next phase prompt.
